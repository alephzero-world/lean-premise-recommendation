### Lean Declaration Type Extraction
In this project, we use the formal type signature of each Lean/mathlib declaration as a node-level semantic feature.
The original MathlibGraph dataset provides declaration names, kinds, modules, namespaces, graph structural features, and dependency edges, but it does not directly include the Lean type of each declaration.
Therefore, we performed an additional offline preprocessing step to extract type information for all declarations.

The type extraction was performed before the main experiments.
First, we took the `name` column from the full declaration node table and created a declaration-name list, where each line contains one Lean declaration name.
Then, using a local Lean/mathlib environment, we directly queried the Lean environment for each declaration name and extracted its corresponding type.
The extracted type information was then merged back into the original node table using the `name` column, producing the final type-augmented node file `nodes_with_types_full.csv` and `nodes_with_types_explicit.csv`.
Results are written in `type` column.

```text
mathlib commit: 534cf0b8f5267c3f20bf52f932ad5f9834187c35
```

## 2. Brief Explanation About the Project
### Introduction
In the past, computer-based mathematics was primarily used to assist with large-scale testing.
However, recently, instances have emerged where AI proposes mathematical ideas while human mathematicians verify and formalize them.
DeepMind’s FunSearch discovered a new configuration for the cap set problem, an old issue in extremal combinatorics.
These proofs were released after review by external mathematicians.

Lean is a functional programming language and a formal proof aid, and actual theorems of modern mathematics are being rapidly formalized.
Currently, Lean is growing into leading ecosystems capable of formalizing mathematical theorems and mechanically verifying them.

The goal of this project is to explore, from a graph machine learning perspective, the problem of recommending relevant premises given a new theorem or declaration, utilizing the dependency graphs of Mathlib (Lean database).
We interpret the dependency relationships between Mathlib declarations not as a simple library structure, but as signals reflecting "which theorems or definitions are likely to be referenced in proofs".
And we test the potential for premise recommendation by GNN-based link prediction.

### Novelty
The novelty of this project lies in three main aspects.

First, we reinterpret the Mathlib dependency network as a prediction problem for formal mathematics-based premise recommendation.
Existing Lean-based research, treats premise selection primarily as a sub-module to complete automated theorem proving.[2, 3]
In contrast, this project focuses on human-oriented premise recommendation to help human researchers find definitions, theorems, and lemmas within Mathlib, rather than complete proof generation.
While [1] analyzed the Mathlib graph from a network science perspective, we transform the same graph into a machine learning task for edge prediction and premise ranking.

Second, we compare two types of dependency: full dependency and explicit human-written reference.
Full graphs reflect mechanical dependencies revealed during the elaboration and compilation processes of Lean, whereas explicit-edge graphs are closer to reference relationships consciously written by human formalizers.
Also, [1] separates explicit edges and compiler/proof-driven edges, but we do not limit this to simple structural analysis and use it as two learning and evaluation graphs.
Through this, we compare machine-visible dependencies and human-written mathematical references in premise recommendation.

Third, we design a node representation specialized for Mathlib declarations for premise recommendation.
While recent premise selection methods often rely on local syntax tree representations [4], we capture the global logical hierarchy of the entire math library.
In Mathlib declarations, name, namespace, module, kind, type, and position within the dependency graph together form meaning.
Therefore, we represent each declaration by combining semantic/type information with structural features such as in-degree, out-degree, PageRank, betweenness, and DAG layer, and use this for GNN-based link prediction.

In summary, the core of this project is that, using a Mathlib-scale dependency graph, we have restructured the existing automated theorem proving-centered premise selection into a predictive framework for premise recommendation that assists human mathematicians in finding proofs in a formal mathematics environment.


### Graph Features & Personalized PageRank
Edges in Mathlib graphs are classified into explicit edges, where `is_explicit` is `True`, and synthesized edges, where it is `False`.
Explicit edges are declarations directly implemented in the code, while synthesized edges are dependencies automatically inserted by Lean as needed.

PageRank was calculated to verify the downloaded data and analyze the characteristics of the graphs.
Additionally, Personalized PageRank (PPR) was calculated for each field of mathematics to explore which fields are associated with which concepts.
Furthermore, subgraphs were generated for each field, and PageRank was calculated within them to identify important nodes within the fields. subgraph_pr is stored in one shared column and used only for qualitative inspection.

### Feature Embedding
Originally, we tried to use PPR for each category as a numeric feature, but the PPR values ​​for almost all categories turned out to be similar.
We further checked this using a Top-k overlap matrix across category-wise PPR rankings. The overlap was high, showing that raw PPR tends to retrieve the same globally foundational declarations across different categories. 
Relative PPR = log(Category_PPR / global_PageRank) reduced this global effect, but its top-ranked nodes were mostly category-local declarations rather than direct premise candidates. Therefore, we used PPR analysis mainly as an exploratory graph analysis tool, not as a final GNN feature.
This appears to be a phenomenon caused by values ​​concentrating at specific hub nodes since the graph is Directed Acyclic Graph (DAG).
We excluded these because using all of them as features would likely make it difficult for the GNN to learn other features.

To generate node feature embedding, we used each column.
- Numeric feature (Size: 5): `in_degree`, `out_degree`, `pagerank`, `betweenness`, `dag_layer` 
- Categorical feature (Size: 8): One-hot vector generated by `kind` column.
- Semantic feature (Size: 64): Two methods were attempted to generate embeddings. Considering the relative size with other features, the dimension of the generated vector was reduced to 64.
    - Case 1: From `name`, `kind`, `module` of node data, generate sentence and use it to create embedding.
    - Case 2: As mentioned in **Lean Declaration Type Extraction**, create embeddings using the mathematical formula information of each node, represented by `type`.

### GNN Architecture
GraphSAGE is used to meet the usage restrictions of the Colab free plan.
- Encoder: Layer Normalization was added to prevent value explosion, and Skip Connections were added to ensure that the original features are not lost.
- Decoder: Since cosine similarity (dot product) cannot distinguish between source and target, the implementation uses concat to determine the direction of the edges.

### Test
Various test metrics were used to verify the performance of the generated model.
The ROC-AUC (Area Under the Receiver Operating Characteristic Curve) score was used to check whether the presence or absence of a node was accurately predicted, and MRR (Mean Reciprocal Rank) and Hit@N were used to investigate whether the actual correct predictions ranked in the top tiers.

In our final explicit-graph experiment, the model achieved:

- ROC-AUC: 0.9957
- MRR: 0.0839
- Hit@5: 0.1151
- Hit@10: 0.2110
- Hit@50: 0.4690
- Hit@100: 0.6017

For the qualitative test on `Polynomial.degree_mul`, the model recovered 12 out of 18 true premises within the Top-100 recommendations.
